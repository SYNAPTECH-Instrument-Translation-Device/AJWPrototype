How a tap becomes a note

Three workers, one meeting point, four lines of glue.

Your win for this lesson: given a finger, the key the camera sees it on, and how hard it tapped, you can say which note plays, how loud, and which line of code decides each part. Takes about 10 minutes.

Three workers

When you run python phone_server.py --camera 1 --tap, three things run at the same time inside one Python process:

  1. The camera thread finds your hand in each frame and works out which paper key each fingertip is over. It writes the answer into a shared dict, latest_fingers.
  2. The strap thread receives about 200 accelerometer samples per second per finger over Bluetooth. Each time a finger spikes, it adds an event to a queue.
  3. The display loop is the program's main loop. About 30 times a second it draws the windows, and it is the only place where camera data and strap data meet.
Camera: process_frame, phone_server.py:227. Strap: TapMonitor, tap_view.py:52. Meeting point: phone_server.py:507–516.

Why join them in the display loop? It already holds a fresh copy of the finger dict for drawing. Matching taps there costs no new threads and no new locks. The price is delay: a tap can wait up to one frame, about 33 ms, before it's matched. That fits the 50 ms tap-to-sound target in METRICS.md, but it's the first place to look if notes ever feel late.

The four steps

1 · Camera: which key is each fingertip on?

fingers = {name: region_at(cal, hand[k].x, hand[k].y)
           for name, k in FINGERTIPS.items()}
# → {"Thumb": 1, "Index": 3, "Middle": 5, "Ring": None, "Pinky": 8}

MediaPipe gives 21 landmarks per hand. The fingertips are numbers 4, 8, 12, 16 and 20 (index tip = 8, per Google's docs). region_at looks up the calibrated key under that point. Note the capital letters: they come from FINGERTIPS in calibration.py:11.

phone_server.py:211, hand_fingers(). Plan 014 added picking the strap hand when two hands are visible.

2 · Strap: did a finger just tap?

dev = abs(m - 1.0)                    # how far from resting gravity (1 g)
if dev > TAP_G and not self.above[f] \
        and host_time - self.last_tap[f] >= REFRACTORY_S:
    self.events.append((host_time, f, dev))

A finger at rest feels 1 g (gravity), so dev is about 0. An event fires only when all three are true:

  • the deviation is over 0.5 g (TAP_G);
  • the previous sample was under it, so one long spike counts once;
  • it has been at least 0.15 s (REFRACTORY_S) since that finger's last tap, so bounce and ringing are ignored.

Strap finger names are lowercase ("index").

tap_view.py:97–112. Both thresholds are guesses until they're tuned on a real recording.

3 · The join: one dictionary lookup

for host_time, finger, peak in tap.pop_events():
    key = fingers.get(finger.capitalize())   # "index" → "Index" → 3
    tap_log.add(host_time, finger, key, peak)

This one line is the whole connection between the two halves of the project. pop_events() empties the queue under a lock, so each tap is handled exactly once. Every tap is logged, including taps that land on no key; those are stored with key 0.

A bug worth remembering. In my first version of the Tap window, the key column always showed -. The camera's dict said "Index" and the strap's names said "index", so every lookup missed and returned None. There was no error to see. Plan 013 fixed it with .capitalize() here and .lower() in render(), and added a test for it (test_render_accepts_camera_finger_names). When two subsystems name the same thing, check that they spell it the same way.

4 · Sound: key → note, peak → loudness

note     = base_note + key - 1                         # key 1 = 60 = middle C
velocity = int(40 + clamp((peak - 0.5) / 2.5, 0, 1) * 87)  # 40 … 127

MIDI notes and velocities both run from 0 to 127 (mido: Message Types). The paper keys are numbered left to right in chromatic order, so each key to the right is one semitone up. A note is stopped by a timer, not by your finger. play() records "stop at now + 0.3 s", and update(), which runs every frame, sends note_off once that time has passed.

sound.py:9–37. The fixed 0.3 s is a stand-in until there's a way to detect a finger lifting off.

One open question

--tap-hand right currently looks for the hand MediaPipe labels "Left" (phone_server.py:412). That follows MediaPipe's older rule that labels assume a mirrored, selfie-style image. Google's current Hand Landmarker page says labels refer to the subject's own hands and that only a mirrored image swaps them. If that's true for your camera, the mapping is backwards. Your first live test will settle it: wear the strap, show only that hand, and see whether the Tap window's key column fills.
